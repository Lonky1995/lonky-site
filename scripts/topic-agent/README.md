# 选题 agent

监控抖音热榜和小红书赛道内容，每天推几条能做的选题。设计成挂 cron 常驻运行。

```
采集 → 存快照 → 比对历史算信号 → 去重 → DeepSeek 生成 → 否决清单 → 推送
```

## 核心思路：看变化率，不看绝对值

一条已经冲到榜首的热点，等你做完内容早就过去了。真正有用的是**还在半山腰但涨得快**的。

所以打分里增速权重（0.6）高于绝对热度（0.4），且必须存**时间序列快照**——单次快照永远算不出增速，只能看见已经爆完的东西。

相关度是**乘数**不是加数：抖音热榜八成是娱乐八卦，不相关的话题再热也应该归零，否则会淹掉一切。

## 装 & 跑

```bash
npm i -D playwright && npx playwright install chromium
export DEEPSEEK_API_KEY=...           # 和站点其他 AI 功能共用

npm run topic:login                   # 首次：依次扫码登录抖音和小红书
npm run topic:dry                     # 只看信号，不烧 token
npm run topic:run                     # 完整跑一次
```

挂 cron（每天两次）：

```cron
20 7,19 * * * cd /path/to/lonky-site && npx tsx scripts/topic-agent/run.ts >> /tmp/topic-agent.log 2>&1
```

推送到飞书群机器人（可选）：设 `LARK_WEBHOOK_URL`，没设就只写文件。
报告固定输出到 `data/topic-agent/latest.md`。

## 文件职责

| 文件 | 碰网络 | 可测 | 说明 |
| --- | :---: | :---: | --- |
| `config.ts` | ✗ | — | **人设、栏目、阈值、否决清单。定位变了改这里。** |
| `signals.ts` | ✗ | ✅ | 增速、相关度、分类、去重。核心逻辑 |
| `suggest.ts` | ✓ | 部分 | prompt 构造和否决清单可测，模型调用不可测 |
| `render.ts` | ✗ | ✅ | 报告渲染，推送渠道共用 |
| `store.ts` | ✗ | ✅ | 快照与运行记录 |
| `sources.ts` | ✓ | ✗ | 采集层，唯一脆弱的地方 |
| `run.ts` | ✓ | ✗ | 编排 |

分层的意义：**采集挂了不影响其余部分**，而采集是唯一会因平台改版而失效的环节。

## 几个刻意的设计

**否决清单跑在模型之后，且是确定性正则。** 模型再怎么飘，割韭菜话术也进不到推送卡片里——这比在 prompt 里叮嘱可靠得多。被拦下的建议会保留在报告里，方便回头调词典。

**单个关键词命中不够格。** 相关度曲线是 1 命中→0.10、2→0.45、3→0.80，而门槛是 0.15。一个词撞上可能是巧合（"曝光""更新"在娱乐八卦里天天出现），两个词同时命中才算信号。

**归一化会删掉短标记。** 平台给话题打的 `【热】``【新】` 每次不一样，不删的话同一话题跨快照会拿到不同 key，增速就永远算不出来。只删 3 字以内的，更长的括号内容当正文。

**每个 source 独立失败。** 一个挂了不影响其他的，全挂才退出。定时任务最怕某天平台改版导致整个 agent 静默停摆。

**去重回看 14 天。** 不去重的话持续热点会天天重复推送，很快就没人看推送了。

## 已知限制

- **`sources.ts` 没有对线上验证过。** 接口过滤条件（`/hot\/search\/list/` 等）可能需要按实际请求调整。首次跑建议用 `--headed` 看着，零命中时先查这里。
- **首次运行没有历史，全部话题都是 `newcomer`，算不出增速。** 至少跑两次之后信号才有意义。
- **登录态会过期**，大约几周。全部采集源同时零命中基本就是这个原因，重跑 `--login`。
- **抖音热榜是泛榜**，与这个账号相关的话题本来就少。某天一条建议都没有是正常的，连续两天为空才该查采集。

## 测试

```bash
npm run test:topic
```

覆盖信号计算（增速、分类、相关度、边界）、否决清单、模型输出解析、报告渲染、存储往返。
采集层没有自动化测试——它依赖真实登录态和线上页面。
